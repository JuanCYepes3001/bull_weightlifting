## Bug #1 — Filtros de productos admin silenciosamente rotos (Crítico)

### Síntoma
La página `/admin/products` mostraba todos los productos sin posibilidad de filtrar, aunque existía el componente `AdminProductFilters` completo con UI de búsqueda, categoría y estado.

### Causa raíz
Triple falla desconectada:
1. `getAdminProducts()` no aceptaba parámetros — ignoraba cualquier filtro
2. `page.tsx` solo leía `saved` de `searchParams`, ignoraba `search`, `category`, `status`
3. `AdminProductFilters` nunca fue importado ni renderizado en la página — era un componente huérfano

### Fix
- **`src/lib/queries/admin.ts`** — `getAdminProducts` ahora acepta `filters?: { search?, category?, status? }` y aplica `.ilike("name")`, `.eq("category_id")`, `.eq("is_active")` según corresponda
- **`src/app/admin/products/page.tsx`** — lee los 3 params de `searchParams`, fetcha `getAdminCategories()` en paralelo, renderiza `AdminProductFilters` sobre la tabla

### Lección
Un componente de filtros que emite URL params solo funciona si la página los lee Y la query los aplica. Cualquier eslabón roto en la cadena produce silencio, no error.

## Bug #2 — Race condition en stock durante checkout (Crítico)

### Síntoma
Overselling posible: si dos usuarios compraban el mismo producto simultáneamente, ambos pasaban la validación de stock y el stock quedaba negativo.

### Causa raíz
El decremento usaba un valor de stock leído segundos antes del `UPDATE`:
```typescript
// Stale read → race condition
.update({ stock: v.stock - item.quantity })
```
Dos requests concurrentes leían `stock = 5`, ambas escribían `5 - 2 = 3`. Stock real debería ser 1.

### Fix
- **`supabase/migrations/014_decrement_stock_fn.sql`** — función PostgreSQL `decrement_stock(p_variant_id, p_qty)` que ejecuta `UPDATE ... WHERE stock >= qty` en una sola instrucción atómica. Si stock es insuficiente lanza excepción `'insufficient_stock'`.
- **`src/types/database.ts`** — agregado tipo `decrement_stock` a la sección `Functions`
- **`src/app/actions/checkout.ts`** — reemplaza el loop de `.update()` por `supabase.rpc("decrement_stock", ...)` con rollback de la orden si falla

### Acción pendiente
⚠️ Ejecutar `supabase/migrations/014_decrement_stock_fn.sql` en Supabase Dashboard → SQL Editor antes del deploy.

### Lección
Ver [[conceptos/pagos-verificacion-manual]] — el patrón correcto para operaciones sobre inventario es siempre un `UPDATE ... WHERE condición` atómico, nunca un select-then-update desde JavaScript.

## Bug #3 — Middleware no protege rutas de admin (Alto)

### Síntoma
Cualquier usuario autenticado con rol `user` podía acceder a `/admin/*`. El middleware dejaba pasar la request y solo el layout hacía redirect, pero ya era tarde.

### Causa raíz
El bloque de verificación estaba vacío:
```typescript
if (user && isAdmin) {
  // Role check happens in admin layout via server component  ← no-op
}
```

### Fix
**`src/lib/supabase/middleware.ts`** — agrega llamada a `supabase.rpc("get_user_role")` dentro del bloque. Si el rol no es `"admin"`, redirige a `/` desde el middleware, antes de que la request llegue al layout o Server Component.

```typescript
if (user && isAdmin) {
  const { data: role } = await supabase.rpc("get_user_role");
  if (role !== "admin") {
    return NextResponse.redirect(new URL("/", request.url));
  }
}
```

La RPC `get_user_role` ya existía en la DB (definida en [[proyectos/bull-weightlifting]]) y en los tipos. No fue necesario crear nada nuevo.

### Por qué el layout solo no es suficiente
El middleware corre en el Edge antes de que Next.js renderice nada. Un redirect en el layout implica que Next.js ya ejecutó la autenticación, cargó datos y empezó a renderizar. El middleware es la barrera correcta.

## Bug #4 — `sale_price null` renderiza `$` sin número (Alto)

### Síntoma
Si un producto tenía `is_on_sale = true` pero `sale_price = null` (dato inconsistente en DB), el componente mostraba `$` sin valor.

### Causa raíz
La condición `isSaleActive` no verificaba que `sale_price` existiera. El operador `?.` de TypeScript evita el crash pero produce `undefined`, que React renderiza como nada.

### Fix
**`src/components/shop/ProductCard.tsx`** — cambia la condición del bloque de precio:
```typescript
// Antes
{isSaleActive ? (

// Después
{isSaleActive && product.sale_price != null ? (
```
Un producto con oferta activa pero `sale_price = null` ahora cae al `else` y muestra el precio regular. También se eliminó el `?.` redundante en `.toLocaleString()` — si el guard pasa, el valor está garantizado.
